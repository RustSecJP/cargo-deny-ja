# bans {#bans}

bans チェックは、特定のクレートを deny（または allow）したり、同じクレートの複数のバージョンを見つけて対処したりするためのものです。

```bash
cargo deny check bans
```

## 使用例 - 特定のクレートを禁止する {#use-case---denying-specific-crates}

あるクレートがどうしてもプロジェクトに合わず、取り除かなければならないことがあります。しかし、取り除いても、ささいな変更で忍び込んでくるのを防ぐものは特にありません。たとえば、`cargo update` を実行したら推移的に入ってきた、という場合があります。また、ワークスペース全体のどこかで、すでに依存しているクレートの既定のフィーチャを通じてそのクレートが入ってくるときに、`default-features = false, features = ["feature-without-the-thing"]` の指定を忘れてしまう、という場合もあります。

たとえば、私たちは以前 OpenSSL に依存していました。TLS を提供する多くのクレートで、OpenSSL が「既定」になっているからです。これは非常に面倒でした。個人の環境でも CI でも、Windows に OpenSSL の開発用ライブラリをインストールしておく必要があったからです。私たちはすべての依存を、ずっとすっきりした `native-tls` や `ring` クレートを使うように切り替えました。今では、OpenSSL がうっかり墓場からよみがえらないことを確かめられます。

## 使用例 - 重複したバージョンを見つける {#use-case---duplicate-version-detection}

プロジェクトが大きくなり、外部の依存が増えるほど、同じクレートの複数のバージョンを持つ可能性は高くなります。これは、Rust のエコシステムにある、次の 2 つの基本的な性質によるものです。

1. Cargo の依存解決は、あるクレートに対するすべてのバージョン制約を、同じバージョンに解決しようとします。しかし、それができない場合には、[複数のバージョン](https://stephencoakley.com/2019/04/24/how-rust-solved-dependency-hell)を使うことをまったく問題にしません。
1. Rust には、非常に多くの（今も増え続けている）クレートがあります。メンテナーごとに、自分のクレートにかけられる時間や労力は異なります。依存についての考え方や、依存をどのくらいの頻度で更新すべきか（すべきでないか）についての考え方も異なります。そのため、別のクレートのどのバージョンを使いたいかについて、クレートどうしの意見がいつも一致するとは限らないのは避けられません。

同じクレートの複数のバージョンを許すというこのトレードオフは、Rust を始めたばかりの多くの人にとって、cargo がとても快適に使える理由の 1 つです。しかし、どのトレードオフにも言えるように、代償もあります。

1. より多くのパッケージを**取得**しなければなりません。これは特に CI に影響し、開発者にも影響します。
1. **コンパイル時間**が増えます。これは CI と開発者に影響します。
1. **ターゲットディレクトリのサイズ**が増えます。これは開発者や、静的な CI 環境に影響することがあります。
1. 最終的な**バイナリのサイズ**も増えがちです。これは利用者に影響することがあります。

ふつうは、ビルドのログをいつも見ているのでもないかぎり、同じクレートの複数のバージョンがあることにはあまり気づきません。しかし、上で述べたように、これは作業の流れに小さな不便を**確かに**もたらします。

cargo-deny の重複の検出は、cargo の動作を「正す」ためのものではありません。重複に注意を向けてもらい、その状況にどう対処するかを、情報にもとづいて決められるようにするためのものです。

* 重複しているクレートについて、エコシステムのほかの部分とそろったバージョンを使うように、あるクレートに PR を出したいと思うかもしれません。
* そのクレートは実はすでに更新されていて、メンテナーがまだ新しいバージョンを公開していないだけかもしれません。その場合は、新しいバージョンを公開してもらえるか頼めます。
* semver の上では互換性がないとされていても、実際には互換性があるかもしれません。その場合は、クレートのコード自体を変えずに、1 つ以上のクレートに一時的にパッチを当てて、別のバージョン要件を使うようにできます。
* すべてのバージョンについて「最新・最高」であることが、それほど重要でないこともあります。その場合は、自分のプロジェクトで、推移的な制約に合う低いバージョンを指定するだけで済みます。
* 最後に、特定の複数バージョンのケースを気にしない場合は、特定のバージョンを 1 つ以上無視するように cargo-deny に伝えるだけで構いません。状況はいずれ自然に解消されます。
